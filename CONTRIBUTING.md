# Contributing

This repository contains proprietary, closed-source software. It is not open source merely because source code may be visible or because contributions may eventually be accepted. All rights remain reserved under [LICENSE](LICENSE).

## 1. Before Contributing

Read `LICENSE`, this document, and [CLA.md](CLA.md). External contributions are not solicited or accepted automatically. A contribution may be considered only when the maintainer has requested or authorized it and the contributor has satisfied the applicable contribution and rights requirements.

## 2. Issues

Use Issues only for appropriate project discussion, documentation defects, or authorized planning. Do not disclose vulnerabilities, credentials, private data, or confidential information. Security reports must follow [SECURITY.md](SECURITY.md).

## 3. Pull Requests

Pull Requests are proposals, not permissions or guarantees of review, acceptance, merge, compensation, or inclusion. The maintainer may reject, close, modify, request changes to, or accept a Pull Request at their discretion and subject to the CLA and applicable law.

External Pull Requests may require CLA verification before review or merge. The planned flow is documented in `docs/legal/legal-readiness.md`; no automated CLA system is installed by this repository at present.

## 4. Branch Naming

For authorized contributions, use descriptive names such as `docs/topic`, `fix/topic`, or `feature/topic`. Branch conventions may be changed by the maintainer. This does not grant permission to create or distribute derivative versions of the software.

## 5. Commit Conventions

Use concise, descriptive commits and avoid secrets, generated credentials, unrelated changes, or third-party material without verified rights. A commit convention and signing policy are `TBD`.

## 6. Tests

Changes should include appropriate tests or a written explanation of why tests are not applicable. The planned testing strategy is in [docs/testing-strategy.md](docs/testing-strategy.md). Do not connect to real user data or production resources without explicit authorization.

## 7. Documentation

Update the relevant documentation and identify changes to ownership, privacy, security, synchronization, or permissions. Documentation contributions are still subject to this policy and the CLA.

## 8. Code Quality

Follow the existing architecture, security requirements, tenant isolation rules, and review feedback. Do not introduce dependencies or licenses incompatible with the proprietary product without prior approval.

## 9. Security

Do not use public Issues or Pull Requests for vulnerability reports. Follow [SECURITY.md](SECURITY.md), do not expose secrets, and stop testing if another user's data or a destructive condition is encountered.

## 10. Intellectual Property

The project remains proprietary. A contribution does not make the project open source, does not grant the contributor rights to distribute the project, and does not change `LICENSE`. Contributors must have sufficient rights to submit their contribution and must not submit third-party material without compatible authorization.

## 11. Contributor License Agreement

Before an external contribution is accepted, the contributor may be required to agree to [CLA.md](CLA.md) or another written instrument approved by the maintainer. Agreement is not automatic from opening a Pull Request. The final acceptance mechanism is `TBD`.

## 12. Review Process

The maintainer may review scope, technical quality, security, provenance, dependency licensing, documentation, and compatibility. Approval by one reviewer does not guarantee merge. A Pull Request must not be merged while a required CLA, rights check, security check, or review remains incomplete.
